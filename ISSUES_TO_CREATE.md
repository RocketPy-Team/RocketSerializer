## Issue 4

**Title:** `ENH: Support multiple nosecones in the parser and notebook builder`

**Body:**

### Context

`rocketserializer/components/nose_cone.py` currently picks the first nosecone
found in the `.ork` file and ignores any additional ones:

```python

```

Multistage rockets and some unconventional designs can legitimately have more
than one nosecone (e.g. on staged sections), so the parser silently dropping

- [ ] `parameters["nosecones"]` becomes a list of nosecone dicts (or remains a
      single dict when there is only one, with backwards-compatible handling).
- [ ] `NotebookBuilder` generates one `NoseCone(...)` cell per nosecone with
      unique variable names.
- [ ] At minimum, log a warning when more than one nosecone is detected, until
      full support lands.
- [ ] Add an example or test exercising the new path.

### Additional Resources

- File: `rocketserializer/components/nose_cone.py`.
- Related issue: #29 (multistage rockets).

## Issue 8

**Title:** `ENH: Support multiple simulation databranches in .ork files`

**Body:**

### Context

PR #40 fixed an `IndexError` in the parser by scoping datapoint extraction to
the **first** `<databranch>` only:

> `.ork` files with multiple simulations or recovery events can have secondary
> branches with fewer columns, causing IndexError when accessing labels by
> index.

This is a pragmatic workaround, but it means information from secondary
branches (recovery events, multiple simulations, etc.) is silently discarded.

### Definition of Done

      respective label sets.
- [ ] The user can choose which simulation/branch to extract from (CLI flag
      or auto-detection of the "main" branch).
- [ ] Each branch's labels are read from its own `types` attribute, not
      assumed to share indices with the first branch.
- [ ] Behavior is backwards-compatible: if no flag is given, default to the
      current "first branch" behavior.
- [ ] Add a test using a multi-branch `.ork` file (e.g. the new `Anonymous--Delta`
      example added in PR #40).

### Additional Resources

- Related PR: #40 (commit "FIX: Use only first databranch for datapoint extraction").

## Issue 10

**Title:** `ENH: Harden burnout detection against indexing edge cases`

**Body:**

### Context

PR #40 patched two edge cases in `__get_parameter` for stored simulation
results:

1. `isinstance(position, np.int64)` did not match `np.intp` or plain Python
   `int`.
2. After NaN filtering, the array can be shorter than the original
   datapoints list, making the burnout position index out of bounds.

The current fix accepts any `(int, np.integer)` and **clamps** the position
to the valid range with a warning. Clamping silently masks the underlying
problem (the burnout index is no longer aligned with the filtered array).

### Definition of Done

- [ ] Replace the clamp-with-warning with proper index translation: when NaN
      filtering is applied, recompute the burnout position on the **filtered**
      array so the index is always meaningful.
- [ ] Keep type-robust handling of integer indices.
- [ ] Add unit tests for: pure-NumPy `intp` indices, Python `int` indices,
      datasets where the original burnout index would now exceed the filtered
      array length.
- [ ] Remove any now-stale clamp/warning logic.

### Additional Resources

- Related PR: #40 (commit "FIX: Handle integer position types and out-of-bounds in stored_results").
- File: `rocketserializer/parser.py` (or wherever `__get_parameter` lives).
